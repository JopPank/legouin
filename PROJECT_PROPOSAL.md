# Le Gouin Trip Manager

## Project proposal

### Overview

Le Gouin Trip Manager is a mobile-friendly, shared web app for planning a group trip. Eight participants, organized into four couples, can coordinate meals, track communal gear, and record trip expenses. Changes should appear for other signed-in participants without requiring a manual refresh.

The first release is scoped to one trip and a known group of eight participants. The data model can be extended later if the group needs multiple trips, more participants, or individual expense splits.

### Goals

- Give all trip participants one shared source of truth for plans and checklists.
- Make common updates quick on a phone, including marking gear as packed.
- Attribute meals, gear claims, and expenses to the relevant couple or participant.
- Restrict trip data to authenticated participants.
- Reflect database changes in connected clients in near real time.

### Proposed technology

| Area | Technology | Purpose |
| --- | --- | --- |
| Web application | Next.js, React, TypeScript, App Router | Application pages, components, and server/client boundaries |
| Styling | Tailwind CSS | Responsive layout and visual styling |
| Authentication and data | Supabase Auth and PostgreSQL | Sign-in, relational trip data, and access control |
| Live updates | Supabase Realtime | Notify clients when shared records change |
| Hosting | GitHub Pages with GitHub Actions | Build and deploy the static Next.js export |

The Supabase publishable/anonymous key may be used by the browser only when Row Level Security (RLS) is enabled and policies restrict access to trip participants. Never expose a Supabase service-role key in client code or a `NEXT_PUBLIC_` environment variable.

### Initial feature scope

1. **Participant access:** Participants sign in and have a profile associated with one of four couples.
2. **Meal planner:** Participants view meals by trip day and see which couple is responsible.
3. **Gear checklist:** Participants view gear by category, claim items, and mark items as packed.
4. **Expense tracker:** Participants record who paid and the amount. The initial split is equal across the four couples.
5. **Live collaboration:** Connected clients refresh relevant data when shared records change.

### Data model

The initial schema can use four application tables, with a small `couples` lookup table to keep couple assignments consistent. The following SQL is a starting point for a single-trip deployment; access-control policies and the Realtime publication must also be configured before the app is exposed to participants.

```sql
CREATE TABLE couples (
    id SMALLINT PRIMARY KEY CHECK (id BETWEEN 1 AND 4),
    name TEXT NOT NULL
);

INSERT INTO couples (id, name) VALUES
    (1, 'Couple 1'),
    (2, 'Couple 2'),
    (3, 'Couple 3'),
    (4, 'Couple 4');

CREATE TABLE profiles (
    id UUID PRIMARY KEY REFERENCES auth.users (id) ON DELETE CASCADE,
    full_name TEXT NOT NULL,
    couple_id SMALLINT NOT NULL REFERENCES couples (id)
);

CREATE TABLE meal_plan (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    day_number INT NOT NULL CHECK (day_number > 0),
    meal_type TEXT NOT NULL CHECK (
        meal_type IN ('Breakfast', 'Lunch', 'Dinner', 'Snacks')
    ),
    assigned_couple_id SMALLINT REFERENCES couples (id),
    menu_details TEXT,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (day_number, meal_type)
);

CREATE TABLE gear_checklist (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    item_name TEXT NOT NULL,
    category TEXT NOT NULL,
    is_communal BOOLEAN NOT NULL DEFAULT TRUE,
    claimed_by_user UUID REFERENCES profiles (id) ON DELETE SET NULL,
    is_packed BOOLEAN NOT NULL DEFAULT FALSE
);

CREATE TABLE expenses (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    description TEXT NOT NULL,
    amount NUMERIC(10, 2) NOT NULL CHECK (amount > 0),
    paid_by_user UUID REFERENCES profiles (id) ON DELETE SET NULL,
    split_type TEXT NOT NULL DEFAULT 'equal'
        CHECK (split_type IN ('equal')),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

The `UNIQUE (day_number, meal_type)` constraint assumes the group plans one entry per meal type per day. Remove or revise it if the group needs multiple entries, such as separate snack assignments.

### Access control and data integrity

Before connecting the frontend:

- Enable RLS on every application table.
- Require an authenticated user whose profile belongs to the trip before allowing access to shared trip data.
- Limit profile edits so a participant cannot change another participant's name or couple assignment.
- Restrict inserts, updates, and deletes to authenticated trip participants; define separately which fields each participant may change.
- Add the required tables to the Supabase Realtime publication.
- Review policies using participant accounts, including attempts to read or edit another user's profile.

For a fixed group of eight, participant enrollment can be handled by an administrator rather than open self-registration. If the app later supports multiple trips, add a `trips` table and membership relationship, and scope every policy and query to the active trip.

### Local setup

Prerequisites: Node.js with npm, a Supabase project, and VS Code.

```bash
npx create-next-app@latest gouin-trip-manager --typescript --tailwind --app
cd gouin-trip-manager
npm install @supabase/supabase-js
npm run dev
```

Create a `.env.local` file in the project root with the Supabase project URL and publishable/anonymous key:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=your-publishable-or-anon-key
```

Use the actual values from the Supabase project settings. Do not commit `.env.local`.

### Supabase client

Create `lib/supabaseClient.ts` and fail clearly when required configuration is missing:

```ts
import { createClient } from '@supabase/supabase-js';

const supabaseUrl = process.env.NEXT_PUBLIC_SUPABASE_URL;
const supabaseAnonKey = process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY;

if (!supabaseUrl || !supabaseAnonKey) {
  throw new Error('Supabase URL and publishable key must be configured.');
}

export const supabase = createClient(supabaseUrl, supabaseAnonKey);
```

### Implementation sequence

1. Create the Next.js application and configure environment variables.
2. Create the Supabase tables, seed the four couples, enable RLS, and add policies.
3. Implement sign-in and participant profile management.
4. Build the meal planner, gear checklist, and expense tracker with typed data models and loading/error states.
5. Add Realtime subscriptions for the tables displayed by each feature, then remove subscriptions when components unmount.
6. Test access policies with separate participant accounts and verify updates across two browser sessions.
7. Deploy the app and configure its production environment variables.

### Acceptance criteria

- A non-participant cannot read or modify trip data.
- An authenticated participant can view and update the shared meal plan, gear checklist, and expenses according to the configured policies.
- A gear item marked packed in one session appears packed in another active session without a manual reload.
- Expense amounts are positive, and meal assignments refer to one of the four configured couples.
- The interface works at mobile and desktop widths and communicates loading and database errors clearly.

### Deployment and operating notes

GitHub Actions builds and deploys the static Next.js export to GitHub Pages on pushes to `main`. Configure the public Supabase URL and key as repository variables, and confirm the custom domain's DNS and HTTPS status in GitHub Pages before launch. Keep database schema changes in versioned migrations so local, preview, and production environments stay consistent.

The equal expense split is recorded as the initial product rule; this schema does not calculate reimbursements or settle balances. A later expense-settlement feature should define how to handle uneven participation, reimbursements, and rounding before implementation.
